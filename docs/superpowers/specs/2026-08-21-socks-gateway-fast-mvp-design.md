# SOCKS Gateway 快速可用 MVP 设计

## 1. 文档状态

- 日期：2026-08-21
- 状态：已在对话中确认，等待书面规格复核
- 目标仓库：`x1aodai/metacubexd-socks-gateway`

## 2. 产品目标

把现有 `metacubexd-socks-gateway` 精简成一个面向单管理员、单台 Ubuntu
VPS 的 SOCKS5 网关。首要目标是尽快获得可部署、可操作、不会在节点故障时
泄漏直连流量的版本。

首版必须做到：

- 固定提供 `10001` 至 `10010` 共 10 个 SOCKS5 端口；
- 全局维护一个节点库，预计日常使用约 10 个节点，但不设置硬性数量上限；
- 每个节点都可以在不同端口中承担前置节点或落地节点；
- 每个端口独立绑定任意数量账号；
- 同一账号可以绑定任意数量端口；
- 每个端口支持一跳或两跳链路；
- 每一跳独立支持固定、自动最优和故障切换；
- 节点池成员、顺序和链路层数均可由管理员手动调整；
- 故障时只允许在既定候选节点中切换，绝不回退到 `DIRECT`；
- 配置应用失败时保留或恢复上一份可用配置。

## 3. 快速交付原则

1. 优先复用已有的管理员认证、节点解析、订阅同步、Mihomo 进程管理、配置校验、
   加密状态文件和修订回滚。
2. 不拆分微服务，不引入数据库，不新增插件或通用抽象层。
3. 先打通节点、账号、10 个端口、单跳/双跳和 Docker 部署，再处理非阻塞的视觉细节。
4. Web 面板只围绕日常任务设计，不保留通用 Mihomo 仪表盘的信息架构。
5. 配置生成采用确定性纯逻辑，便于用测试覆盖端口隔离、链路和禁止直连等核心约束。

## 4. 保留与删除范围

### 4.1 保留

- `apps/server` 中的 Nitro 服务端和现有管理员登录流程；
- `packages/agent` 中的 Mihomo supervisor、节点导入、订阅、加密持久化、校验和回滚；
- `packages/ui` 中仍被极简面板使用的基础组件、表单、认证客户端和 Gateway API 封装；
- 单容器全功能服务端构建；
- Docker secrets、只读敏感配置、健康检查和持久化 volume；
- Mihomo 及原项目各自要求保留的许可证和来源声明。

### 4.2 删除或从产品构建中移除

- `apps/desktop` 及 Electron、托盘、自动更新、本机 helper；
- TUN、系统代理和桌面端网络接管；
- Overview、Proxies、Rules、Connections、Traffic、Logs、Config、Profiles、Control、Setup
  等通用 MetaCubeXD 页面；
- Monaco/YAML 编辑器、WebDAV、PWA、全局快捷键；
- 图表、主题市场、多主题和多语言切换；
- 与单管理员 SOCKS 网关无关的远程 Mihomo 面板连接流程。

删除工作必须以构建和测试持续通过为前提。仍被保留代码依赖的公共组件先解除依赖，再删除，
不采用一次性大范围删目录的方式。

## 5. 运行架构

首版沿用现有 all-in-one 服务端：Nuxt/Nitro 提供 Web 和控制 API，Gateway Agent 在同一
运行环境中管理 Mihomo 子进程，Mihomo 承担 10 个 SOCKS5 listener 和节点路由。

部署保持为一个 Docker Compose 服务和一个持久化 volume：

- 管理 Web 默认监听 `127.0.0.1:8080`；远程访问通过现有 Nginx/Caddy 模板或 SSH
  隧道提供，不直接公开 Mihomo Controller；
- Mihomo Controller 仅监听 `127.0.0.1:9090`；
- SOCKS5 监听 `0.0.0.0:10001-10010/tcp`；
- UDP 默认关闭且首版不提供开启入口；
- 不提供 HTTP/mixed 代理端口；
- 不修改宿主机系统代理、TUN 或防火墙，真实部署需要另行明确授权。

为减少首次交付风险，首版继续使用现有 host network 部署方式。对外可达面由监听地址控制，
而不是额外增加容器网络层。

## 6. 状态模型

现有加密状态文件 `gateway.enc` 升级为版本 2，继续使用原子的加密写入和修订快照，不引入
SQLite。

### 6.1 端口

状态中始终存在 10 个不可删除的端口槽位：

```text
PortConfig
  id: 1..10
  port: 10001..10010
  enabled: boolean
  credentialIds: string[]
  hops: HopConfig[]  // 长度只能是 1 或 2
```

- 启用端口前必须至少绑定一个启用账号，并至少配置一跳；
- 端口可以临时停用，但端口号不可修改；
- `credentialIds` 不设业务数量上限；
- 不同端口之间的账号、路由、状态和活动节点互不影响。

### 6.2 跳点

```text
HopConfig
  mode: manual | auto | failover
  nodeIds: string[]
```

- `manual` 要求恰好一个节点；节点故障时只显示异常，不自动改变模式或节点；
- `auto` 要求至少一个候选节点，由 Mihomo `url-test` 选择健康且延迟较低的节点；
- `failover` 要求至少一个有序候选节点，由 Mihomo `fallback` 按顺序故障转移；
- 两跳链路的两跳可以使用不同模式和不同候选集合；
- 节点可跨端口、跨角色复用，但同一条两跳链路不能连续使用同一个节点；
- 系统不得根据健康状态自动增加或删除跳点。

管理员通过“添加一跳”把单跳改为双跳，通过删除任意一跳把双跳改为单跳。这两类操作都是
明确的人工配置变更。

### 6.3 账号

账号继续由现有 Gateway Credential 模型保存，密码只在创建或轮换时返回明文。端口通过
`credentialIds` 建立多对多关系：一个端口可绑定多个账号，一个账号可绑定多个端口。

账号被停用时，所有绑定关系保留但不再写入 listener。删除账号时同步移除各端口中的引用；
因此失去最后一个启用账号的端口会被停用并拒绝转发。

### 6.4 节点库

节点库继续接收三类来源：

- 订阅 URL；
- 分享链接或批量文本粘贴；
- 手工添加。

节点拥有稳定内部 ID，路由只保存 ID，不依赖可能变化的显示名称。节点可被自由启停和删除。
删除订阅中的单个节点会在该订阅下记录排除项，后续自动刷新不会把它无提示地重新加入；管理员
重新导入或恢复该节点时才清除排除项。

## 7. Mihomo 配置生成

配置生成器从版本 2 状态一次性生成全部受管对象：

1. 为每个端口的每一跳生成独立、带端口命名空间的 proxy group；
2. `manual` 映射为 `select`，`auto` 映射为 `url-test`，`failover` 映射为 `fallback`；
3. 单跳 listener 的 `proxy` 指向该端口唯一跳点组；
4. 双跳时为落地候选生成端口私有的派生代理，使用 Mihomo `dialer-proxy` 指向前置组；
5. 原始节点配置不被修改，因此同一个节点仍可安全地被其他端口或角色复用；
6. 每个 listener 只写入该端口绑定且已启用的账号；
7. 停用或缺少合法前置条件的端口不生成 listener，防御性兜底组只能包含 `REJECT`；
8. 受管规则最终指向对应端口链路，不生成 `DIRECT` 回退。

受管对象名称使用稳定前缀和端口号，避免与导入节点及原配置冲突。生成器拒绝启用端口中的
循环链路、重复监听端口、缺少账号、缺少跳点和未知节点引用。

## 8. 配置应用与故障处理

所有变更进入现有串行 transaction 队列，避免并发应用覆盖：

1. 克隆当前状态并应用用户变更；
2. 执行业务校验；
3. 生成完整 Mihomo YAML；
4. 用 `mihomo -t` 校验；
5. 为当前状态和活动配置创建加密快照；
6. 启动或重载 Mihomo；
7. 检查 Controller，并检查全部已启用 listener；
8. 只有运行验证通过才持久化新状态；
9. 任一步失败都恢复上一份活动配置和状态，并向 Web 返回可操作的中文错误。

现有“固定节点连续健康失败后自动改为 failover”的行为必须删除。固定模式只报告健康状态，
不会静默修改用户选择。

删除正在使用的节点前，API 返回受影响端口列表供 Web 二次确认。确认删除后：

- 候选组仍有节点时继续使用剩余节点；
- 某一跳失去最后一个节点时删除该跳；
- 双跳因此剩余一跳时成为单跳；
- 端口没有任何跳点时自动停用；
- 全过程仍需通过完整配置校验和回滚流程。

这属于管理员主动删除产生的结构变化，不属于系统自动切换单跳/双跳。

## 9. Web 面板

登录后直接进入“端口”，不设置首页仪表盘。产品只保留四个一级入口。

### 9.1 端口

固定显示 10 行端口，字段为端口号、启停状态、绑定账号数、单跳/双跳、当前活动链路和健康
状态。编辑面板允许：

- 多选账号；
- 配置第一跳的模式和节点；
- 添加第二跳；
- 删除任意一跳；
- 调整 failover 节点顺序；
- 保存前预览完整链路；
- 确认保存后立即事务式应用；
- 查看最近一次应用结果。

### 9.2 节点

提供订阅 URL、分享链接/文本和手工添加入口。列表只显示名称、协议、来源、延迟、健康状态、
启用状态和引用端口，并支持检测、启停、刷新订阅和批量删除。

### 9.3 账号

提供创建、停用、删除和密码轮换。账号详情使用端口多选框维护允许访问的端口。密码只在创建
或轮换成功后显示一次。

### 9.4 系统

只显示 Web、Agent、Mihomo 和 10 个 listener 的运行状态，以及重新应用当前配置、订阅刷新、
管理员密码修改和版本信息。

界面固定中文、单一浅色风格，无主题、多语言、图表、动画或高级 YAML 编辑。常用操作最多
两层，应用成功或失败必须在当前上下文中明确显示。

## 10. API 边界

沿用现有 `/api/control/gateway` 认证、CSRF 和 mutation token 机制，资源收敛为：

- `/ports`：读取 10 个端口并事务式更新单个端口；
- `/nodes`、`/imports`、`/subscriptions`：事务式管理全局节点库；
- `/credentials`：事务式管理账号并返回端口绑定；
- `/status`：返回服务、端口、跳点和活动节点状态；
- `/revisions`：仅供自动回滚和系统页显示最近结果，不恢复完整审计中心页面。

首版不增加服务端草稿模型。表单未保存内容只存在浏览器内；管理员确认保存后，对应 mutation
直接进入第 8 节的完整校验、应用和回滚事务。系统页的“重新应用”只重新生成并验证当前已保存
状态，不创建第二套配置来源。

响应不得包含节点订阅原始 URL、账号密码、Controller secret、master key 或完整运行配置。日志
和错误也必须脱敏。

## 11. 旧状态迁移

首次加载版本 1 的单端口状态时执行一次确定性迁移：

- 保留全部账号、节点来源、订阅和修订；
- 把原单端口配置迁移到 `10001`；
- 原 `manual`、`auto`、`failover` 映射为第一跳的对应模式；
- 原启用账号全部绑定到 `10001`；
- 其余九个端口初始化为停用；
- 迁移前创建原始加密文件备份；
- 迁移结果必须先通过 Mihomo 校验，失败时保持版本 1 文件不变并停止启动。

## 12. 安全边界

- 单管理员认证沿用现有密码哈希、会话 Cookie、CSRF 和登录限速；
- 加密状态文件、修订和审计文件保持 `0600`；
- 管理 Web 和 Mihomo Controller 默认只绑定 loopback；
- SOCKS 端口必须认证，不支持匿名访问和跳过认证网段；
- 不向 Mihomo 生成 `DIRECT` 候选或直连兜底；
- UDP、IPv6 SOCKS 放行、TUN 和系统代理均不在首版范围；
- Docker secrets 不写入镜像、仓库、日志或 API 响应；
- 不在本项目工作中自动修改 VPS 防火墙、系统代理或其他宿主网络设置。

## 13. 测试与验收

### 13.1 自动化测试

- 状态版本 1 到版本 2 的迁移测试；
- 账号与端口多对多绑定测试；
- 10 个 listener 的配置快照测试；
- 单跳和双跳配置生成测试；
- 三种跳点模式及两跳混合模式测试；
- `dialer-proxy` 链路、循环拒绝和命名冲突测试；
- 删除节点、删除账号和端口自动停用测试；
- 配置校验失败与运行验证失败的回滚测试；
- 固定模式绝不自动改为 failover 的回归测试；
- 禁止 `DIRECT`、UDP 和匿名 listener 的契约测试；
- API 认证、CSRF、脱敏和并发 mutation 测试；
- Web 端口、节点、账号、系统四个流程的组件测试；
- 完整 Web 构建和 Docker 镜像构建。

### 13.2 可用 MVP 验收

- `10001-10010` 可以同时监听并独立连接；
- 正确账号只能访问已绑定端口，错误或未绑定账号被拒绝；
- 一个账号能同时使用多个端口，一个端口能接受多个账号；
- 节点可在多个端口和不同跳点角色中复用；
- 管理员能手动在单跳和双跳之间转换；
- 固定、自动最优和故障切换均按每一跳独立工作；
- 一个端口切换或失败不影响其他端口；
- 所有候选节点故障时相应端口停止转发且无直连泄漏；
- 无效配置不会替换当前可用配置；
- 容器重启后账号、节点、绑定和端口链路保持不变；
- 管理 Web 能完成全部日常操作，无需编辑 YAML。

本地自动化通过后才能标记本地 MVP 完成。真实 VPS、真实节点故障切换和外部出口 IP 检查单独
记录为 `pass`、`fail` 或 `not-run`；没有实机证据时不得把它们报告为已通过。

## 14. 明确不做

首版不包含：

- 桌面客户端、移动端应用；
- 多管理员、角色权限、租户和计费；
- 流量配额、限速、账单和长期统计；
- 通用 Clash/Mihomo 规则编辑；
- 三跳及以上链路；
- 自动改变链路跳数；
- UDP、TUN、系统代理和 HTTP/mixed 代理；
- 集群、高可用控制面和远程节点编排；
- 插件机制、Webhook 和第三方通知；
- 主题、多语言、PWA 和 WebDAV。

## 15. 交付节奏

在依赖安装、现有基线构建和本地 Mihomo 可用的前提下：

- 可操作 MVP 目标为 7 至 10 个有效开发日；
- 含完整自动化、Docker 和稳定性修复的版本目标为 12 至 18 个有效开发日；
- 真实 VPS 验收依赖部署授权、测试节点和可访问的服务器环境，不计入纯本地开发承诺。

时间范围是工程估算，不以牺牲认证、禁止直连、配置回滚或端口隔离为代价压缩。
